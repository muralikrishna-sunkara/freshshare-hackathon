- Org permissions go through `requireOrgRole`; anyone without the role gets 404 (so viewers don't see the bulk-claim form). The last admin can't be removed or demoted.
- Bulk claims reserve each picked listing with the same atomic available → reserved guard and create a normal pending claim per item, held until the listing's pickup window ends. Status: pending → in_progress (first item confirmed) → partially_completed → completed, or cancelled.
- Site admins: `User.role = admin` (seeded `admin@demo.freshshare.de`). `/api/admin/*` answers 403 to non-admins. `/admin` approves fridges and organizations.
- Admin reports queue: dismiss, or "remove listing", which sets the listing to `removed`, cancels any active reservation (and updates a bulk claim it belongs to) and resolves every open report on that listing. Early-access stats count all rows by role and source; the CSV export is admin-only, `no-store`, and prefixes cells starting with `= + - @` so spreadsheets don't run them.
- Seed photos are the kit's 25 Wikimedia Commons photos (credits on `/credits`, from `data/seed-photos/CREDITS.md`). Each is uploaded once per seed run as `seed/<name>.webp` and shared by every listing that uses it.

It never adds available food within 2.2 km, so the pitch's 2 km map stays exactly the hand-written listings. API tests seed with `history: false`.
- `npm run db:clean-test` (or the "App database seed" workflow with `clean_test` ticked) deletes `@example.test` accounts and everything they created, without a full reset.
- Find food has a Map / List switch (`?view=list`). The list view is a "Browse food" page: filters and saved searches (kept in this browser only) on the left, a search bar (`?q=`, matches title, description, category, area, giver, fridge) with sort (`?sort=nearest|soonest|newest`) and Save, then a 3-column card grid (photo with category badge, best-before, origin, description, portions/weight, public area or fridge, pickup until, allergens, dietary tags, giver badge and rating) and nearby fridges. Clicking a card opens the usual detail panel.
- Notifications (T2.1): one `Notification` table (type, title, body, link, read/emailed timestamps). `services/notify.ts` is called from the claim, chat, admin-approval and listing code paths and from the minute housekeeping (lapsed holds, pickup window ending within an hour, once per listing). New listings alert people whose alert area covers them (max one per person per 20 min). The header bell gets its unread count over SSE that polls Postgres every 3 s (works with several api tasks); `/notifications` has mark-all-read. `waitlist_offer` exists as a type for T2.3 but nothing sends it yet.
- Email goes through `lib/email.ts`: Amazon SES on AWS (Terraform domain identity with DKIM/SPF/DMARC, sender locked to notifications@freshshare.de in IAM), Mailpit locally through its HTTP send API (no SMTP library, to avoid nodemailer's open advisories), `log` by default in dev, `memory` in tests. Only claim_received, claim_confirmed and new_message are emailed, with a per-user opt-out on the profile page. We don't use Floci.
- Impact (T3.2): counted from collected pickups only. kg is the entered weight or 0.4 kg per portion; CO₂e is 2.5 kg per kg (kit PRODUCT.md) and water 190 L per kg (FAO 2013 blue-water footprint). All shown as estimates with the method note. A person's impact (given + rescued, listings, fridge check-ins, last 6 months) is public aggregates only, like the profile. An organization's impact is everything collected with its `organizationId` (last 12 months, pickup runs, givers helped, categories); public for approved orgs, otherwise members and site admins.
- The share card is a 1200x630 PNG rendered on the api from SVG with sharp (`/api/impact/users/:id/card.png`, `/api/impact/organizations/:id/card.png`), since we aren't on Next.js and `next/og` isn't available. The api image installs DejaVu fonts so text renders. Share uses the Web Share API with the image file where supported, else shares or copies the link; Download is always there.
- The organization impact report is a one-page A4 PDF made with pdfkit (`/api/impact/organizations/:id/report.pdf`), for org members of any role and site admins.
- QR pickup (T2.6): confirming a pickup creates a random 6-digit `pickupCode`, shown only to the receiver as a QR code and digits. The QR holds the pickup URL with `?code=`, so the giver scans it with the normal phone camera (no in-app scanner), lands on the pickup page with the code filled in, and taps Confirm handover (`POST /api/claims/:id/verify`). "Mark collected" stays as a fallback.
- Waitlist (T2.3): `ListingWaitlist` rows with a position. You can join only while the food is reserved or held for someone else (the "Someone else was quicker" case offers it straight away). When a claim is cancelled, declined, lapses, is cancelled from a bulk run or by blocking/suspension, `offerToNext` gives the first person a 30-minute exclusive hold (`Listing.reservedForUserId/reservedUntil`) and a `waitlist_offer` notification. While held, the listing is hidden from everyone else's map and only the holder can reserve (enforced inside the same atomic update). The minute housekeeping passes expired holds to the next person, then reopens the listing.
- Moderation (T2.5): profile reports already existed. Blocking (`Block` table) works both ways: neither sees the other's listings on the map or by link, neither can reserve from or message the other, open pickups between them are cancelled, and they leave each other's waitlists. The blocked person isn't told. Admins can suspend from a report (or `POST /api/admin/users/:id/suspend`) with a reason: the account can't sign in or use an existing session (checked in `requireAuth` on every request), its open listings are removed, its open pickups cancelled, and the reason is shown at sign-in. Suspensions are listed on `/admin` with "Lift suspension".
- Nearby alerts + push (T2.2): the alert area already existed in the data model; `/api/alerts` now lets people set it (centre = home, 500 m to 5 km, optional categories) from the profile page, with the existing one-alert-per-20-minutes limit and no alerts from blocked people. Every in-app notification is also sent as web push to each device the person enabled (`PushSubscription`, VAPID through the `web-push` library; dead endpoints are removed on 404/410). The VAPID key is one P-256 PEM generated by Terraform; the api derives the public key. `public/sw.js` only handles push and notification clicks (no offline cache yet, so deploys are never stale).
- Recurring listings (T2.4): "Repeat on a schedule" on your own listing makes a `ListingSchedule` from it (text, details, photos), with weekdays, a time (Europe/Berlin) and how long pickup stays open. The minute housekeeping posts it once per due day; the `lastPostedOn` update is the lock, so several api tasks never double-post. Homemade food can't repeat (it must be cooked fresh and has the 48 h limit). Manage them at `/me/recurring` (edit days and time, pause, delete). Anyone can use it, not only businesses, up to 10 schedules.

## Listing edits, list-first browsing, K1 photo autofill (feedback from Krish)
- **Edit listing**: `PATCH /api/listings/:id` for the giver while the food is still available. Once someone has reserved it, the giver must decline or finish that pickup first, so the receiver never gets food that differs from what they reserved. The place stays fixed; Post again moves it.
- **List first, any distance**: Find food opens in the list view, with no distance filter (up to 50 km, nearest first). Tapping a selected km chip clears it. `?view=map` and `?km=` keep views shareable.
- **K1 photo autofill**: Claude (`claude-opus-5-5` at low effort, structured outputs validated with zod, server-side refusal fallback) suggests the title, category, label, dietary tags and allergens. The photo is resized and re-encoded first so EXIF/GPS never leaves our servers; nothing is stored. Raw meat/fish and non-food photos are refused. The key sits in a hand-made Secrets Manager secret (`freshshare-dev/ai`), so it never appears in Terraform state or CI logs.
